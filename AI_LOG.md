## Key prompts

1. _"let's write together a Claude.md, what is very important is that the structure looks like this src/..."_ (from the frontend session, but it set the two-repo split: frontend owns the UI/contract, backend is a stateless proxy with its own repo and its own `AI_LOG.md`/README) — established that the backend should expose exactly one `/api/analyze` contract and never leak the Gemini key.
2. _"each type should be in it's own separate file"_-style requests for stricter structure carried over into the backend's own layering: `LLMClient` as a `Protocol` in `app/services/llm/base.py` so `app/services/analysis.py` never imports the Gemini SDK directly, and `app/core/errors.py` as the single place mapping domain errors to HTTP status codes.
3. _"so why is the live not working correctly? it uses the same token"_ and _"what is wrong on back"_ — the live demo was returning `502` on every upload; diagnosed by reproducing the exact call the backend makes (`GeminiClient.generate_structured`) locally against the real deployed key and document, not by guessing from logs.
4. _"we need to have error handling for 429"_ — turned the diagnosis into a code change: distinguish a quota/rate-limit failure from any other provider failure, instead of treating every Gemini error identically.
5. _"what about splitting the pdf texts, and running summaries on it, and then running a summary on joint"_ — a proposed fix (chunking) that was rejected after checking whether it actually addressed the observed failure (it didn't — see below).

## Where AI got it wrong

- **Shipped `gemini-3.6-flash` as the default model without checking its free-tier capacity.** It's a newer/preview-tier model, and Google throttles it much harder on the free tier than established models — observed directly as `5 requests/minute` and `20 requests/day` quotas, and independently of quota, roughly a 50% `503 "high demand"` failure rate on real structured-output calls. This made the public demo link fail for most visitors, which is exactly the scenario the brief's Definition of Done is built around ("osoba z zewnątrz otwiera link do demo i bez instrukcji... widzi podsumowanie"). Found by reproducing the failure locally with the real key and the real document — first a plain `generate_content` call (worked), then the actual structured-output call the app makes (failed consistently), which isolated the problem to capacity/quota rather than a code bug. Fixed by switching the default to `gemini-flash-lite-latest` (a rolling alias to Google's current stable lite model) after confirming 4/4 real-document calls succeeded with schema-valid output — see commit `94198f8`.
- **Treated every Gemini failure the same way, including quota exhaustion.** The original retry logic (`app/services/analysis.py`) burned its one internal retry even when Gemini had just said "you're out of quota" — retrying immediately against an exhausted quota can't succeed, so the second call was pure waste, and the user always saw a generic `502` with no indication of what was actually wrong. Fixed in commit `e1fa5a2`: a `429` from Gemini is now caught as a distinct `LLMRateLimitedError`, skips the wasted retry, and is surfaced to the frontend as a real `429` — which the frontend already had correct handling for (`kind: "transient"`, "Spróbuj ponownie"), it just never got exercised before because the backend was masking the real status code.
- **A proposed "fix" (chunking the document and summarizing per-chunk) would have made the capacity problem worse, not better**, and was rejected before writing any code. The `503` failures weren't related to request size — a 2,000-character excerpt failed exactly like the full 20,000-character document — so chunking would have multiplied the number of Gemini calls per analysis (more exposure to the same flaky model, faster quota burn, lower end-to-end success rate) without touching the actual cause.

I've read and understood every line that ended up in this repo, including tracing through why each of the above failures actually happened (reproducing them locally against the real API) rather than accepting the first plausible-sounding fix.
